# Logical model (G1 draft, non-normative)

Status: draft for the G1 gate, 19 October 2026. It describes what the Workspace stores and why, not a schema. The physical design follows ADR 0001 (one canonical relational store, PostgreSQL as measured in `spikes/db/`), and the RDF graph and search index are rebuilt from it. It does not define OpenRiC: where it touches the standard it cites the published term, and the S-GATE rule in `ROADMAP.md` applies.

Two of the hard constraints in `SPECIFICATION.md` shape every table below. The model is built to production standard, so each entity has an owner, an audit trail and a deletion rule from the start. And there are no enumerations: every controlled value is a row in a vocabulary table.

## 1. Identity

Every entity has two identifiers, and neither is a database row number.

| Identifier | Form | Purpose |
|---|---|---|
| UUID | Version 7, generated by the Workspace | The internal key. It never appears in a public IRI. |
| Persistent IRI | `{institution base IRI}/{entity kind}/{slug or UUID}` | The `@id` in every export, graph node and SPARQL triple. It survives renaming, moving in the hierarchy and migration. |

: Identifiers of every entity

A graph node for an entity carries that entity's persistent IRI, as Graph Primitives invariant 7 requires (OpenRiC v0.51.0). An identifier from another system, such as a Heratio `urn:ahg:ric:<type>:<id>` or an AtoM slug, is kept as an alternative identifier with its source, so migration can be traced (WS-013).

## 2. Vocabularies (no enumerations)

A single pattern holds every controlled value:

- **Vocabulary**: an IRI, a title, the source (OpenRiC, RiC-O, ICA-EGAD, or local), and whether the institution may add to it.
- **Concept**: an IRI, its vocabulary, labels per language (BCP 47), a definition, an optional broader concept, and a deprecation flag with a replacement. Concepts are never deleted, only deprecated, so old assertions stay readable.

Every column that would otherwise be an enumeration is a reference to a concept: record-resource level, agent kind, relation type, role, date type, activity type, rule type, assertion status, review status, publication state, language-value state, file availability. Where OpenRiC or RiC-O publishes the vocabulary, the Workspace loads it and does not mint its own: `vocab/role-type`, `vocab/date-type`, `vocab/activity-type`, `vocab/rule-type`, and the RiC-O 1.1 classes and properties. Local concepts carry an IRI under the institution's base.

Rules that depend on a value, such as "only a published record may appear in discovery", test the concept's IRI, never a label or a position in a list.

## 3. Entities

The kinds follow RiC-CM 1.0 and are serialised with RiC-O 1.1 classes only; anything RiC-O lacks uses a term from the published OpenRiC extension ontology (`https://openric.org/ns/ext/v1`, 1.4.0).

| Entity | RiC-O class on export | Notes |
|---|---|---|
| Institution | `rico:CorporateBody` | The tenant. Every other row belongs to exactly one. |
| Repository | `rico:CorporateBody` holding records | ISDIAH; contact details with `openricx:ContactPoint`. |
| Record set, record, record part | `rico:RecordSet`, `rico:Record`, `rico:RecordPart` | Level is a concept. The hierarchy is a navigational view over part-of relations, not the whole model (hard constraint). |
| Instantiation | `rico:Instantiation` | A carrier of a record; files attach here. An individual physical medium is an `openricx:Carrier`. |
| Agent | `rico:Person`, `rico:CorporateBody`, `rico:Family` | ISAAR(CPF). An occupation held over time is an `openricx:Occupation`. |
| Activity | `rico:Activity` with `rico:hasActivityType` | Production and accumulation are activity-type concepts, not classes (RiC-O 1.1 has no such classes). |
| Place | `rico:Place` | |
| Rule | `rico:Rule` with `rico:hasOrHadRuleType` | Access restrictions and security classification, with `rico:beginningDate` and `rico:endDate`. |
| Date | `rico:Date`, `openricx:DateRange` | Literal endpoints on `rico:beginningDate` and `rico:endDate`; type on `rico:hasDateType` from the date-type vocabulary. |

: Entities and how they are exported

Every entity row carries its institution, its persistent IRI, its created and updated stamps with the acting user, and a soft-delete stamp. Nothing is removed outright while an assertion or an export refers to it.

## 4. Relations and assertions

A relation is a first-class row, not a foreign key, because WS-003 and WS-006 need to say who connected two things, from what source, and whether that is still believed.

- **Relation**: source entity, target entity, relation type (a concept that resolves to a RiC-O property or relation class), and optional dates. It exports as a reified RiC-O relation (`rico:relationHasSource`, `rico:relationHasTarget`) plus the shortcut property.
- **Role**: optional, a concept from the role-type vocabulary. It exports as `openricx:relationHasAgentRole`, or `rico:creationWithRole` on a creation relation. This is service issue #11.
- **Relation language**: optional, a language concept, exported as `openricx:relationHasLanguage`.
- **Assertion**: every relation, and every descriptive value that can be disputed, is held through one or more assertions. An assertion records who asserted it (a user, an import, a model), when, from what source, on what basis, its assertion status and its review status (both concepts), and which earlier assertion it supersedes. This is service issue #17.

Two assertions about the same fact can coexist; neither overwrites the other, and a superseded assertion stays for audit. An assertion made by a model exports with the Inferred-Provenance markers: `prov:wasGeneratedBy`, `openricx:assertionStatus` "inferred", `openricx:confidence`, `openricx:inferenceReceipt`, and `openricx:humanConfirmed` once a person confirms it. An assertion without those markers is an asserted fact, as that profile requires.

## 5. Language values

Each descriptive text (title, scope and content, history and the rest) is a set of language values rather than one column. A value has a BCP 47 tag, a state (draft, reviewed, published, withdrawn: concepts), whether it is the original or a translation, and the assertion it came from. The original is never overwritten by a translation or an inference (hard constraint). Fallback between languages is explicit and recorded in the export, never silent (WS-005).

## 6. Files

A file belongs to an instantiation and records its MIME type, size, SHA-256 at ingest, the last fixity check and its result, its rights (a rule), and its availability (a concept). Files are served only through the Workspace, which checks access on every request; there is no direct storage URL (WS-007).

## 7. Publication and access

Publication is a state on each record and on each language value, not a flag on a page. Every public channel, which means discovery, the API, OAI-PMH, exports, search, caches and the RDF projection, reads through the same access decision, and the decision denies by default (WS-008, WS-011). The RDF and search projections are rebuilt only from what that decision allows, so an unpublished value cannot reach the graph.

## 8. Audit

Every change writes an audit row in the same transaction: actor, time, entity, the fields before and after, and the request it came from. The audit log is append-only and is part of every backup. Restore is tested against it (WS-011).

## 9. Projections and checks

The RDF graph and the search index are projections, rebuilt from the store. Before a rebuilt graph replaces the live one, it passes the checks in `conformance/README.md`: every `rico:` term is defined by RiC-O 1.1, every `openricx:` term by the published extension ontology, and graph nodes carry the persistent IRI. The OpenRiC reference service applies the same checks (`openric:rebuild-graph`, service v0.17.25).

## Open questions for G1

1. Whether multi-tenancy is one database per institution or row-level security in one database. The DB spike measured PostgreSQL but not row-level security with a second role.
2. Whether descriptive values that cannot be disputed (an identifier, a file's checksum) also go through assertions, or only relations and disputable text.
3. How the institution base IRI is chosen and kept when an institution moves domain.
